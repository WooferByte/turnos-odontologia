Es la segunda excepción registrada de C-01 (la primera, D123, son sus 8 escenarios) y vale solo para este change. Condición del autor: las tareas van **agrupadas por tema**. Los grupos son: preparación (1); dominio (2); persistencia (3); un grupo por escenario (4 a 11: E1, E2, E3, E4, E5, E7, E6 y E12, este último con la validación de entrada); API (12); demo y README (13); verificación final (14). E7 va antes que E6 para dejar juntos los dos escenarios de borde.

Reglas de trabajo para todos los grupos (no son tareas):

- **TDD estricto.** En cada grupo el test que falla (RED) va antes que el código (GREEN). Después de cada paso se corre `python -m pytest` desde `backend/`. Un grupo termina con toda la suite en verde.
- **Si un test nace verde** (pasa sin tocar código de producción, como puede pasar en E4 y E7 porque la regla ya quedó escrita en un escenario anterior): no se da por bueno. Se rompe a propósito la línea de producción que debería protegerlo, se comprueba que el test falla, se restaura y se deja anotado en el resumen del grupo.
- **Sin mocks** de sesión ni de repositorio. Los tests de `unit/` no tocan la base. Los datos salen de `tests/factories.py` y son ficticios (RN-PR-01).
- **Nombres, firmas y formas**: los de `design.md` (D1..D19). Si falta algo, no se inventa: se vuelve al design.
- **Errores** (RN-GL-02, D135; design D4 y D6): la validación de entrada se informa toda junta en un `EntradaInvalida` (`422`); las reglas de negocio, solo con la entrada válida y de a una (primero `RN-AG-10d`, después el solapamiento, que es una regla y puede llevar dos códigos).
- **Commits**: solo con el ok del autor (regla dura 10), en español y con prefijo. Puntos sugeridos: uno `test:` al cerrar cada RED y uno `feat:` al cerrar cada GREEN, para que el historial muestre el test antes que el código.
- Rutas relativas a `backend/` salvo que se indique otra cosa.
